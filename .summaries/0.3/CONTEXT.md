## 1. Project snapshot

- **What:** Desktop Blackjack simulator — Kelly betting, card counting, basic-strategy advisor, per-shoe analytics, replay/shoe history, player profiles.
- **Tooling:** C++17, SFML 3.0, CMake >=3.10, Catch2 v3.6 (tests). Style: `.clang-format`.
- **Dependencies already linked:** SFML Graphics/Window/System/Audio/Network. JSON: nlohmann/json (vendored in `include/nlohmann`).
- **Build:** run `cmake --preset "GCC 13.3.0 x86_64-linux-gnu"` -> binary dir `out/build/GCC 13.3.0 x86_64-linux-gnu/`.
- **Test:** run `ctest --test-dir out/build/GCC\ 13.3.0\ x86_64-linux-gnu --output-on-failure` (or the `Blackjack2Tests` binary). Test binary links **only** `SFML::Graphics`; main exe (`Blackjack2`) links all modules incl. Audio+Network.
- **Entry:** `main.cpp` -> `Game::run()`.

## 2. Architecture map (real module layout)

State is owned by **`Game`**; rendering/input/settlement are delegated friends.

| Concern | Owner |
|---|---|
| Loop, mode dispatch | `Game` (`run()`/`update`), `AppMode` enum — new modes = new enum values + update() handling |
| Round/turn state machine | `RoundEngine::tick(dt, Game&)` (Friend) |
| Settlement / BJ check | `HandEvaluator` (Friend) |
| Presentation | `GameRenderer`, `HUD`, `Panel`, `StatBox`, `FontManager`, `Graphics` — no game-state mutation |
| Input | `InputHandler` (Friend) |
| Basic-strategy advice | `BasicStrategy::getRecommendedAction(...)` -> "Book" advisor + Correct/Deviated feedback |
| Card counting | `BasicStrategy::updateCount(style)`, `trueCount/estimateEdgePercent` — styles `HI_LO`,`REKO`; counts kept live in `runningCount`/`backgroundRunningCount`; edge % calibrated to Hi-Lo TC only |
| Shoe boundary | `Game::resetShoeAnalytics()` / `startNewShoe()` — one choke point bumps `shoeGeneration`, zeroes `ShoeAnalytics shoe_`, re-seeds counts; only bankroll carries across a shoe |
| Persistence | `PlayerProfile` (nlohmann/json) — stores `PlayerStats stats` + table settings; backward-compatible schema required |

**Data model in `include/GameRecord.hpp`:** `PlayerStats` (career, persisted); `ShoeAnalytics` (per-shoe HUD, zeroed each shoe boundary); `RoundRecord`/`HandOutcome` (round/hand records for replay+stats); `DeviationRecord` (advisor deviation history).

## 3. Testing contract (non-negotiable for new logic)

New **game logic** is tested headless first, before any UI:
- Use `Game(bool headless)` + `setDeck(std::vector<Card>)` for a deterministic dealt sequence.
- Drive via `startTestRound()`/`startTestRound(seats)` and public actions (`hit`/`stand`/`doubleDown`/`split`/`surrender`/`confirmBet`).
- Read results through `*ForTest()` accessors (`hudStateForTest`, `shoeAnalyticsForTest`, `advisorFeedbackForTest`, `runningCountForTest`, ...).
- Tests live in `tests/*.cpp` and are registered in `CMakeLists.txt` under `Blackjack2Tests` — add new files there or they won't run.
- Keep pure logic SFML-Graphics-only; gate Audio/Network behind headless-safe paths.

## 4. Conventions to preserve

- **Mode dispatch via enum:** extend `AppMode`; each mode gets its own state machine mirroring Replay/Pause wiring, not ad-hoc booleans.
- **Additive JSON schema:** new profile fields must be optional with defaults when absent (existing saved profiles keep loading).
- **Two-tier stats:** career (`PlayerStats`, persists) vs per-shoe (`ShoeAnalytics`, resets). Do not conflate.
- **Centralize shared side effects** in existing choke points; don't sprinkle new I/O.

## 6. Open decisions / risks (confirm before acting)

1. **Counting (#6):** extend `BasicStrategy::CountingStyle` + existing `updateCount(style)` dispatch vs. standalone `CardCounter` class. *Recommended: extend the dispatch* — mirrors HI_LO/REKO, less surface area.
2. **Custom Rules ripple (#3):** changing `giveBasicStrategyAdvice()` signature is the riskiest change to test stability. *Recommended:* thread a narrowly-scoped `const GameRules&` into advisor + rules UI only; keep deck-count / soft-17 / DAS / resplit / surrender changes in their own call sites.
3. **Deliverable format:** feature work lands as new files under `include/`+`src/` with mirrored tests, matching existing module naming. (Followed for Feature 7: `SoundManager.{hpp,cpp}` + `tests/test_sound_manager.cpp`.)

4. **Test target links SFML::Audio now (Feature 7):** `Blackjack2Tests` originally linked only `SFML::Graphics`. Because `SoundManager.cpp` is compiled into the test binary and uses `sf::SoundBuffer`/`sf::Sound`, both branches of `CMakeLists.txt` now also link `SFML::Audio`. Decoding buffers / exercising the queue needs no display or audio device, so headless `ctest` stays safe. This is the one deviation from "tests link only Graphics"; to drop it again, remove `SoundManager.cpp` from both targets and revert the two Audio link lines.

5. **SoundManager design (Feature 7):** uses the pImpl idiom — all SFML audio state lives in `SoundManager::Impl`; pure logic (Settings + event queue + counters) is headless-safe and drives the tests. SFML 3 gotchas encountered: `sf::Sound` has NO default ctor (construct from a buffer, re-point via `setBuffer()`); query status with `getStatus() == sf::SoundSource::Status::Playing` (no `isPlaying()`); text uses `setFillColor` and construct `sf::Text` with its font; `Transformable::setPosition` takes a single `Vector2f`; `sf::Music` opens via `openFromFile` (returns bool). Known effect events: card/bet/chip/blackjack/win/lose; music track `theme`.

6. **Driving the dealer reveal headlessly reads a *member*, not the tick arg:** `Game::dealerTurn()` takes no parameter and advances its reveal pacing timers (`DEALER_START_DELAY` / `DEALER_ACTION_DELAY`) using the member `game.deltaTime`, NOT the `deltaTime` passed to `RoundEngine::tick(dt, game)`. Ticking with a large dt alone therefore never moves the dealer. To drive a full PlayerTurn->DealerTurn->settle headlessly you must set `game.deltaTime = 100.0f;` before ticking (see `tests/test_side_bet_round.cpp`).

7. **Suite size now 157 ctest cases:** Feature #1's side-bet logic tests (`test_side_bets.cpp` + `test_side_bet_round.cpp`) were added and the previously-broken compile fixed, so the whole suite builds clean and passes headless over the Graphics-only path. Keep pure logic SFML-Graphics-only and gate Audio/Network behind headless-safe paths; wire the Feature #1 HUD/renderer display into `HUDState`/`GameRenderer` next (UI only, no new game-state mutation).

8. **Strategy Trainer design (Feature 2):** its own state machine (`include/StrategyTrainer.hpp/.cpp`) with pure, headless-safe grading/stats/timed-session logic and a graphics-only `draw()` - no SFML in the logic path, so it runs over the Graphics-only test binary. It grades a chosen action by comparing against `BasicStrategy::getRecommendedAction` (H/D/S/P/R; the game's surrender key 'Y' normalizes to 'R'), tracks accuracy/streaks and can bound a session by wall-clock time via `update()`. An Ace is card **value 1** (values 11/12/13 are J/Q/K), so soft-hand fixtures must build the ace as value 1. Mode wiring mirrors Replay exactly: new `AppMode::StrategyTrainer` + `MenuOption::StrategyTrainer`, Game::update() dispatch, GameRenderer draw+menu-label cases and a dedicated InputHandler::processTrainerEvents() path (declared in InputHandler.hpp). ~Game owns the trainer via unique_ptr with an incomplete type (like Replay); the headless Game(true) ctor skips building it and startTrainerSession guards nullptr. No PlayerProfile change for this feature - persistence stays additive/untouched. Two follow-up cosmetics were added afterward: the trainer clears the window to a royal-purple color instead of drawing felt.png (the felt behind the text is unnecessary), and nextQuestion() re-deals until the player's hand is not a natural blackjack, since a BJ needs no decision.

9. **Hyper speed tier (Feature 2):** added `GameSpeed::Hyper` as the fastest *manual* tier alongside Fast/Normal/Slow/AutoPlay - AutoPlay stays the only fully automated mode; Hyper keeps you driving your own cards at near-max pace, just with dramatically shorter pauses. `include/Constants.hpp` maps it through the single timing table: `NPC_HYPER = 0.05f` (near-instant NPC reactions, ~6x shorter than Normal's 1.0s) and `SUMMARY_HYPER = 0.3f` (result overlay flashes just long enough to read). Both `npcActionDelay()` and `summaryDisplayTime()` switch on Hyper; `afterHandWait()/afterShoeWait()` return 0 for it automatically because they only special-case AutoPlay, so no new automation path is introduced. Wiring touches every GameSpeed consumer: `InputHandler::cycleGameSpeed()` now cycles all five via a size-5 array (`+1`/`-1` wraps with `% 5`) and logs the choice; `GameRenderer` renders the "Hyper" menu label; and `Game.cpp`'s profile-load switch preserves a persisted Hyper instead of falling back to Normal (the enum serializes as an int, so without this case a saved Hyper would silently reset to Normal on reload). No `-Wall/-Werror` flags exist in this project, but all switches were still closed for correctness. Build clean; 158/158 tests pass.

10. **Gamer speed tier (Feature 2):** added `GameSpeed::Gamer` as the refresh-rate-derived tier, "as fast as the hardware allows". Unlike Hyper's fixed constants, Gamer derives its per-step timing from the monitor's refresh rate: one gameplay step advances per frame, so seconds-per-step = 1/refreshRate (e.g. 144Hz ~7ms). Because THIS SFML build's `sf::VideoMode` exposes NO public refresh-rate reader (`VideoMode` has only width/bpp; there is no `DisplayMode`, and `Window` offers only `setVerticalSyncEnabled()`/`setFramerateLimit()`, which don't report a number), the rate is read straight from the OS at full-mode startup via best-effort XRandr on Linux (new `Game::detectMonitorRefreshHz()`, guarded by `#if defined(__linux__) && !defined(__ANDROID__)`) with graceful fallback to `GameTiming::DEFAULT_REFRESH_HZ`, now set to 240 (this user's monitor rate). To keep pure logic headless-safe, the value is injected into `Game` as a `refreshRateHz` member (`setRefreshRateForTest()`/`refreshRateForTest()`) and resolved by a pure helper `GameTiming::gamerStepInterval(hz)` (= 1/hz, collapsing to DEFAULT_REFRESH_HZ for hz<=1). Gamer branches at both timing consumers (RoundEngine npcActionDelay, HandEvaluator summaryTimer); it's wired through every GameSpeed path like Hyper (size-6 cycle array + log line + "Gamer" menu label + persisted in the profile-load switch). New `tests/test_gamer_speed.cpp` (+ registered in CMakeLists) asserts 1/Hz derivation, the <=1Hz/default fallback, Gamer-faster-than-Hyper at high Hz, and the injected-rate seam. **Then (turn 3): Hyper joined the automated tiers too**, so now both Hyper and the refresh-rate Gamer play automatically. Every seat auto-decides via basic strategy like AutoPlay, driven through `GameTiming::isAutoPlaying()` (= AutoPlay, Hyper, or Gamer - new helper) placed at all six state-machine autoplay gates: RoundEngine PlaceBets (Kelly auto-bet + confirm), OfferInsurance, PlayerTurn advancement, Cleanup (round advance) and GameOver (new-shoe advance); plus the InputHandler manual-key block that otherwise lets a human take actions. So both Hyper and Gamer are autoplay (`isAutoPlaying(Hyper)`/`isAutoPlaying(Gamer)` true) yet differ from AutoPlay only in pacing, not automation - Hyper uses a fixed ~1/0.05s-per-step pace while Gamer is refresh-rate-paced (≈1/240s per step). **Then (turn 4): made the dealer reveal match player pace in Gamer/Hyper.** Previously `Game::dealerTurn()` armed its per-card timer from fixed `DEALER_START_DELAY`/`DEALER_ACTION_DELAY` (both 0.5s) that ignored speed, so in fast auto-play the dealer dragged along at ~0.5s/card while players flashed by. Added pure headless-safe helper `GameTiming::dealerRevealInterval(speed, refreshRateHz)` (= gamerStepInterval for Gamer, npcActionDelay(Hyper) for Hyper, else the fixed DEALER_ACTION_DELAY beat) and wired both dealer-arm points in Game.cpp to it - so every reveal is paced exactly like a player action in the automated-fast tiers while all other speeds keep their watchable 0.5s beat (no behavior change there). New `tests/test_gamer_speed.cpp` case asserts Gamer/Hyper match the player intervals and Fast/Normal/Slow/AutoPlay stay at DEALER_ACTION_DELAY. Build clean; 162/162 tests pass (added the dealerRevealInterval case: 161 -> 162).

11. **Casino Simulation — N-thread CPU-maximizing auto-play:** Drafted plan for spawning several independent blackjack instances, each on its own thread playing automatically, behind a single mutable instance count (start at 4), so the next way to "push hardware" is parallelism across many simultaneous games rather than faster pacing. Motivated by Feature #2 speed tiers being done. **(a) Headless-per-instance core (recommended):** Each instance runs `Game(bool headless=true)` — pure round/state machine, no SFML window/texture/sound/replay — on its own `std::thread`, driven by a fixed-timestep `game.update(deltaTime)` loop. This is deliberately NOT `Game::run()` (Game.cpp:163), which polls events + draws against one window and cannot be shared across threads; you also can't safely share one SFML OpenGL context between threads, and N windows each with their own context is heavy/flickery. **Confirmed fork to decide at implementation:** whether to additionally render an aggregated casino-floor overlay (needs a GameRenderer path + its own aggregator window — optional polish) or run headless-only for pure CPU throughput. Plan targets headless MVP first; rendering optional afterwards. **(b) Config seam:** add `CASINO_INSTANCE_COUNT` (+ clamping to `std::thread::hardware_concurrency()` at spawn for graceful degradation on cores < instances) as the single tunable, easy to change later. **(c) Concurrency/persistence hazard — THE core requirement:** persistence currently funnels every instance through one fixed path (`Player::saveProfile()` -> `getSavePath()` -> `$HOME/.local/share/blackjack/saves/player_profile.json`), and each shoe completion does a read-modify-write of that single JSON's `longHistory`; with N threads this is last-writer-wins clobbering = lost shoe records / corrupted JSON / failed saves. **Mitigation (recommended):** give each instance its own profile file (`player_profile_<i>.json`) so there is zero cross-thread disk contention, and aggregate their histories/stats into a master record through a mutex-guarded merge in the manager using RAII `std::lock_guard` (mirroring the existing static `std::mutex logMutex` + lock_guard pattern in Logger). Add an atomic-write primitive everywhere: write to a temp file then `std::filesystem::rename` over the target so a crash mid-save never corrupts the active profile. **Alternative if single-history semantics are required:** one shared file guarded by a process-wide mutex with every `addShoeRecord`/save taken under the lock and atomic rename — higher contention, implement only if (b)'s isolation is unacceptable. **(d) Speed-mode wiring:** add `GameSpeed::Casino` so `isAutoPlaying()` returns true and all six autoplay gates fire; casino instances run on a fixed auto-play tick rather than monitor refresh — decide whether they share the player's speed setting or their own. **(e) Ownership/shutdown:** a `CasinoSimManager` owns the N threads, joins them cleanly before exit (no leaked/detached threads), and any shared aggregate is mutex-protected; per-instance mutable state (Deck/Hand/player) stays private to each thread so no locking is needed there. **Risks/unknowns to confirm at implementation:** (1) render headless-only vs overlay — the main fork; (2) isolated-per-instance vs shared-history semantics; (3) bankrolls independent per seat vs a shared total — recommend independent per instance. **(f) Testing (headless, logic-first):** new `tests/test_casino_sim.cpp` (+ CMakeLists registration under Blackjack2Tests, Threads linked on both targets): spawn N headless Games with injected decks, tick concurrently without exception; a concurrency regression test asserting combined history length == sum of per-instance shoes and no corrupted/missing records after simultaneous shoe completions + atomic saves; verify clean thread join. **CMake:** `find_package(Threads REQUIRED)` + link `Threads::Threads` to both targets; ensure `-pthread`. Status: **plan written; implementation in a fresh context window.**
12. **Tournament Mode design (Feature 9):** implemented as a self-contained AppMode state machine (`include/Tournament.{hpp,cpp}`) mirroring the StrategyTrainer/Replay pattern - pure-logic play-out + `draw()` presentation, driven headless-first via an injected shoe and explicit `playHand()`. Reuses existing primitives rather than the timer-based RoundEngine tick loop: `Deck` for the shoe (with Game's reversed-setCards convention), `Hand` for value/soft/pair detection, `BasicStrategy::getRecommendedAction` for seat decisions, and crucially `Player::settle` for payout so bankrolls move exactly as in-game. Key design choices to inherit: forced blind bet is applied via `Player::placeBet()` affordability (unaffordable seats sit out), doubles draw one extra card then stand, surrender is treated as a stand, dealer stands on all-17, and winner selection is argmax with lowest-index tie-break. It does NOT touch PlayerProfile (JSON schema stays additive). Two gotchas this window hit: `Deck::draw()` pops from the back so injected shoes reverse like Game, and this SFML build's HARD basic-strategy table treats hard-13-vs-dealer-8 as a *hit* - so deterministic scenarios must be driven empirically through ctest rather than hand-computed.
