What I'd avoid

One thing I would not put in HUDState is pointers or references to your core game objects, such as:

Player*
Dealer*
Deck*
Game*

or even

Hand&

Those objects contain behavior, not just data, and giving the HUD access to them makes it easy for UI code to accidentally start making game decisions. Keeping HUDState as a plain data structure (plus read-only pointers to statistics, if you like) preserves a clean separation: the game decides what the current state is, and the HUD decides how to present it.

As your UI grows—adding animations, themes, or even replacing SFML with another rendering library—that separation will make the codebase much easier to maintain.

3. Your true count formula is incorrect

I also noticed this:

return runningCount / (deck.size() / (52 * Constants::NUM_DECKS));

This isn't calculating decks remaining.

Suppose:

2 deck shoe
104 cards total
52 cards left

Then

deck.size() == 52

Your formula becomes

52 / (52 * 2)

= 0.5

which says there are 0.5 decks remaining.

There is actually 1 deck remaining.

The number of decks in the original shoe should not be in the denominator.

Instead:

float decksRemaining =
    deck.size() / 52.f;

return runningCount / decksRemaining;

or

return runningCount / (deck.size() / 52.f);
4. Better yet, let Deck compute it

Since the deck knows how many cards remain, I'd move this logic out of Game.

float Deck::decksRemaining() const
{
    return size() / 52.f;
}

float Deck::trueCount() const
{
    float decks = decksRemaining();

    if (decks < 0.25f)
        decks = 0.25f;

    return runningCount / decks;
}
